## 2. 功能一：嵌套审批后父任务自动续跑 ✅

**实现**（`packages/execution/executor.py`）：
- 子任务的"审批恢复 run"（trigger=approval）**成功收尾**后，若其父任务满足全部条件——处于 `awaiting_approval`、无 pending 审批、无 queued/running 的活跃 run、未被请求暂停/取消——则自动入队父任务（`trigger=auto_resume`，新触发类型已加入状态机放行清单），并写事件 `task.auto_resumed`。
- **子 run 失败时不自动续跑**：避免对已知失败步骤立即重试烧真实费用，由人工决定（重试子任务或手动恢复父任务）。
- 子任务在嵌套路径内完成（非审批独立 run）不受影响——那条路径父任务本来就是内联继续的。

**开发中修正的一个边界**：首版把父任务自身的 `awaiting_approval` run 也算作"活跃阻塞"，导致自动续跑永不触发——而那正是要被恢复的状态。已修正为只排除 `queued/running`（真正的冲突源），`awaiting_approval` 的旧 run 作为历史记录保留（与人工恢复路径行为一致）。

**测试**（`tests/test_m3b_recursion.py`，10/10）：
- 新增 `test_nested_approval_auto_resumes_parent`：子任务工具审批批准 → 子任务经审批 run 完成 → **父任务自动续跑成功**（断言 `task.auto_resumed` 事件 + 工作区产物真实落盘），全程无人工干预；
- 原有人工恢复测试更新为自动语义（人工 `POST /resume` 路径仍保留可用，状态机不受影响）。

**语义边界（如实说明）**：env off 时若 kill switch 已打开，自动续跑入队的父任务在执行时会正常走到"步骤必需工具被全局关闭"的可读失败路径——自动续跑不会绕过任何安全检查，它只是替代"人工点恢复"这个动作。

## 7. 诚实声明

1. 自动续跑目前只覆盖"子任务审批恢复 run 成功"这一条路径；若审批针对的是**顶层任务**的工具调用（M3-A 路径），其恢复机制本就是自动的（批准即入队），不受本改动影响。
2. 父任务被自动续跑后若再次遇到未授权工具等拒绝，仍会按既有熔断语义暂停——自动续跑不改变任何拒绝判定。
3. `enqueue_run` 的 `auto_resume` 触发类型与 executor 的收尾钩子是本批新增代码路径，已有专项测试；更复杂的多层嵌套（祖父任务）未构造专项测试，机制上逐层适用但未验证。
4. 浏览器验收的 29 项不含审批中心页的专属交互断言（该页 UI 为本轮新增，由 build 类型检查 + API 既有测试覆盖）；如需页面级断言可在 browser_acceptance.py 增补。
